# ClientSQL generator

This directory contains the canonical, reviewable Python source for Valdi's
SQLDelight-style ClientSQL generator.

The source is divided by responsibility:

- `cli.py` owns command-line parsing and generation orchestration.
- `model.py` defines the schema and query model.
- `sql.py` parses and validates SQL, migrations, parameters, and result shapes.
- `typescript.py` emits generated TypeScript bindings and database classes.

The public Valdi toolchain uses the Bazel
`//compiler/clientsql:clientsql_toolchain` wrapper as its canonical
`sqldelight_compiler` executable. The wrapper invokes the reviewed
`//compiler/clientsql:clientsql` sources, so those sources are the actual input
to local and remote ClientSQL generation; no Git LFS generator binary or
unpublished toolchain release is required. A deterministic standalone zipapp
can still be created at an explicit local path:

```bash
python3 compiler/clientsql/package_clientsql.py --output /tmp/clientsql
```

An explicitly supplied executable can be checked against the canonical source:

```bash
python3 compiler/clientsql/package_clientsql.py --output /tmp/clientsql --check
```

Both the source entry point and zipapp require the same explicit floor-validator
path:

```bash
python3 compiler/clientsql/src/clientsql_main.py \
  --sqlite-validator /path/to/sqlite_316_validator -version
/tmp/clientsql --sqlite-validator /path/to/sqlite_316_validator -version
```

The public Bazel Valdi toolchain selects
`//compiler/clientsql:clientsql_toolchain`. That small runfiles wrapper injects
`//compiler/clientsql:sqlite_316_validator` before invoking the source
generator. This preserves Valdi's established external ClientSQL compiler CLI,
so an internal `@valdi_toolchain//:sqldelight_compiler` can continue to provide
its legacy implementation without receiving a new unsupported argument. The
legacy compiler protocol passes the database class through `-p`, `-c`, and
`-m`; the public wrapper strictly validates that protocol and derives the Valdi
bundle for the OSS generator from the required
`<generated>/<bundle>/src/sqlgen` output layout. Direct source or zipapp
invocations still fail closed if the validator path is absent, cannot execute,
or reports a different SQLite version/source identity.

`clientsql -version` includes a SHA-256 digest over the canonical package
sources plus the exact validator executable's SHA-256, SQLite version, official
source ID, `sqlite3.c` SHA-1, and protocol version. `ClientSqlProcessor` stores
that full identity in its disk-cache metadata, so either source or validator
changes invalidate generated outputs even when the human release number remains
`0.2.0`.
Generator tests execute both the source entry point and packaged zipapp against
the same fixture and require identical version identities and generated bytes.
For a source-tree test run, first build or otherwise supply the verified target
and set `CLIENTSQL_TEST_SQLITE_VALIDATOR` to that executable; the tests do not
fall back to the host Python SQLite library.

## Compatibility with existing ClientSQL implementations

This OSS generator is a new Valdi-specific contract. It has not been shown to
produce SQLDelight-v1 or Snap-internal ClientSQL-compatible TypeScript APIs,
schema behavior, or storage identities. Existing consumers must compare their
generated API surface and revalidate queries, migrations, persistence, and
upgrade behavior before switching generators.

The existing `@valdi_toolchain//:sqldelight_compiler` seam remains the compiler
selection boundary. Keeping that legacy seam means importing these public
sources does not implicitly switch internal consumers to the OSS generator;
the public toolchain wrapper is selected only by the public toolchain repository.

SQL generation targets the SQLite 3.16.0 runtime floor supported by Apple system
SQLite. Schema statements are prepared and executed, generated queries are
prepared as `EXPLAIN` with their exact parameter counts, and every migration
statement is prepared by a validator actually linked to the verified 3.16.0
amalgamation. There is no host-Python SQLite dependency and no finite syntax
blacklist. Non-Apple runtime builds continue to use the separate pinned SQLite
3.53.4 release documented in `third-party/sqlite/README.md`.

Generated database classes keep the caller-facing database name for display,
but derive a canonical lowercase ASCII storage identity from the Valdi module
digest plus a collision-free UTF-16 encoding of that name. The public toolchain
wrapper maps the legacy compiler invocation to the canonical Valdi bundle name,
so identically named databases in different bundles receive different module
digests without changing the established internal compiler protocol. This
prevents two modules from sharing a file accidentally and prevents filesystem
case, normalization, separator, or trailing-character aliases. Names are
limited to 48 UTF-16 code units and may not contain control characters. Schema
versions
are positive 32-bit integers; migration filenames must be unique, contiguous
32-bit versions beginning at 2. Concurrent handles for one storage identity
must present the same length-delimited schema fingerprint.
